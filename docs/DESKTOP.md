# EKVAAR OS — P4 DESKTOP ARCHITECTURE

## 1. DESKTOP PHILOSOPHY

**What is the Desktop?**
The Desktop in EKVAAR OS is a zero-distraction cognitive environment. It is not a storage area for files, and it is not a grid for application icons. It is a pure, minimalist void anchored solely by the KRISHNA Kernel visual interface (the central Orb/Jarvis UI).

**What belongs on the Desktop?**
Only the KRISHNA Kernel.

**What should never appear on the Desktop?**
Files, folders, application shortcuts, transient widgets, or grid icons. 

**Philosophy:**
**Workspace Driven.** The background and ambient environment adapt to the current cognitive Workspace (e.g., Brand vs. Finance), but the physical surface of the desktop remains permanently blank to force focus toward Intent (KRISHNA) rather than Clutter (Files).

---

## 2. DESKTOP OBJECTS

In traditional operating systems, files and folders are "Desktop Objects." In EKVAAR OS, traditional files do not exist.

**Which objects can exist directly on the Desktop?**
None. 

**How should they behave?**
Instead of static objects resting on the desktop, KRISHNA generates **Transient Output Widgets**. If the Founder asks to view a *Metric* or an *Output*, KRISHNA renders an ephemeral window in the center of the screen. When the Founder dismisses it, it vanishes back into the Knowledge Vault. The Desktop is a stage for temporary execution, not a permanent shelf.

---

## 3. DOCK ARCHITECTURE

**Purpose:** 
To provide immediate, one-click access to the three Core Applications designated in P3 (Telemetry, Knowledge Vault, Mission Control) when Voice/Text commands are too slow.

**Maximum Size:** 
Strictly 3 slots.

**Permanent Applications:** 
1. Telemetry
2. Knowledge Vault
3. Mission Control

**Behavior:** 
Autohidden by default. It only appears when summoned to the edge of the screen, preserving 100% of the pixel space for deep work.

**Prioritization Model:** 
**Importance.** The Dock does not change based on frequency or context. The three apps represent the absolute pillars of OS interaction that cannot be replaced by voice. They are permanently locked.

---

## 4. LAUNCHPAD ARCHITECTURE

**Why Launchpad exists:**
It does not. The Launchpad is completely abolished in EKVAAR OS.

**What belongs there:**
Nothing.

**How users access applications:**
The three Core Apps are accessed via the minimal Dock or by commanding KRISHNA ("Open Telemetry"). Because there are no secondary or third-party apps, a Launchpad grid is an unnecessary architectural relic.

---

## 5. MISSION CONTROL ARCHITECTURE

*(Note: As defined in P3, Mission Control is a Core App, not a window-manager expose).*

**Purpose:** 
A high-altitude, strategic visualization of the company's Execution DAG (Directed Acyclic Graph).

**Contents:** 
Nodes representing active *Missions*, *Initiatives*, *Projects*, and *Tasks*, connected by lines of dependency. 

**What problems it solves:** 
When the Founder needs to diagnose why a strategic goal is failing, Mission Control visually highlights the exact bottleneck (e.g., an Agent stuck on a Task waiting for a Decision approval).

**How users use it:** 
As a read-only diagnostic map to oversee the autonomous workforce, interacting only to unblock red nodes.

---

## 6. WINDOW ARCHITECTURE

**Operating Model:** 
**Single Window / Split View (Max 2).**

**Behavior:**
- **Snapping/Stacking:** Free-floating, overlapping windows (stacking) are abolished. They create cognitive load and visual noise.
- When an Application (e.g., Knowledge Vault) or a KRISHNA Transient Widget opens, it opens **Full Screen** (Single Window) by default.
- If comparison is needed, the OS supports a strict **50/50 Split View**. No third window is allowed on a single monitor.
- **Application Lifecycle:** Windows are ephemeral. Closing the window suspends the view state, but the underlying OS data (Knowledge, Metrics) is always live in the persistence layer.

---

## 7. WORKSPACE ARCHITECTURE

**What a Workspace actually is:**
A strict **Cognitive Context Filter**. It is not a separate virtual desktop where different apps are open; it is a global state variable that alters what data KRISHNA and the Apps retrieve.

**Examples:** Founder, Brand, Operations, Finance, Strategy.

**How they behave:**
If the OS is in the "Finance" Workspace:
1. KRISHNA implicitly assumes all vague questions relate to Finance Knowledge.
2. The *Telemetry* app automatically filters to show only burn rate, revenue, and cash flow.
3. *Mission Control* only renders financial DAGs.

**How they are created:**
Dynamically generated by KRISHNA when the Founder establishes a new Domain or Department in the Knowledge Vault.

---

## 8. NOTIFICATION ARCHITECTURE

**What generates notifications:**
- Blocked *Decisions* (An Agent requires Founder approval to proceed).
- Critical *Metric* threshold breaches (e.g., "Server downtime detected").

**What never generates notifications:**
- Agent task transitions (Starting/finishing a standard Task).
- Routine Knowledge indexing.
- Background reasoning loops.

**Priority Levels & Interaction Rules:**
1. **Critical:** Bypasses Focus Mode. Pauses KRISHNA. Requires explicit action (Approve/Reject).
2. **Standard:** Silently badged. Covered during the Morning Briefing.

---

## 9. CONTROL CENTER ARCHITECTURE

The OS Control Center is reduced to the absolute minimum hardware and environmental toggles.

**Included OS Controls:**
- **Audio / Microphone** (Crucial for KRISHNA voice interaction).
- **Workspace Switching** (Quickly shifting the global context filter).
- **Focus Mode** (Mutes all Standard notifications).
- **AI Autonomy Mode** (A global slider adjusting how much capital/destructive action Agents can take without explicit Founder approval).

---

## 10. SEARCH ARCHITECTURE

**Search vs KRISHNA:**
- **KRISHNA** is Generative. ("Read the Q3 report and write an email to investors.")
- **Search** is Deterministic. ("Find the exact Q3 report PDF.")

**Architecture:**
Search **does** exist independently of KRISHNA as a global overlay shortcut (e.g., `CMD+K`). 

**Why:** 
When the Founder knows exactly what *Knowledge* node they want, routing it through KRISHNA's LLM parsing introduces unnecessary latency. Global Search bypasses generative reasoning and hits the Persistence Vector DB directly for instant retrieval.

---

## 11. STARTUP EXPERIENCE

**The First 30 Seconds:**
1. **Boot:** The screen is pitch black. The KRISHNA Kernel visual interface slowly illuminates in the absolute center of the screen.
2. **Context Load:** The OS authenticates the Founder via biometrics/presence and loads the default "Founder Workspace."
3. **The Briefing:** The OS does not wait for a command. KRISHNA proactively speaks the **Morning Briefing**, surfacing the exact number of Missions completed overnight by Agents, and immediately presenting any blocked Decisions that require the Founder's approval to unblock the day's execution.

---

## 12. DAILY OPERATING EXPERIENCE

**How the Desktop Adapts:**

- **Morning (Alignment):** The Desktop is dominated by the KRISHNA visual interface. The Founder speaks approvals for overnight Outputs and unblocks Decisions presented by KRISHNA.
- **Midday (Deep Work):** The Founder shifts into specific Workspaces (e.g., "Brand"). The Desktop remains blank, but the Founder spends hours inside the *Knowledge Vault* editing Outputs, or in *Telemetry* reviewing data.
- **Evening (Brain Dump):** The Founder closes all Apps. The Desktop returns to the blank KRISHNA interface. The Founder speaks a stream-of-consciousness dump of the day's events, which KRISHNA silently indexes into Knowledge and overnight Tasks.
- **Weekly Review:** The Founder shifts to the "Strategy" Workspace and opens the *Mission Control* application full-screen to analyze the holistic execution graph of the company.
